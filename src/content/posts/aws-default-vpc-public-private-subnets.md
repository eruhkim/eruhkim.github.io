요즘 AWS에서 새 서비스를 올릴 때면 VPC부터 이렇게 나눈다.

- **퍼블릭 서브넷**: 로드 밸런서, NAT 게이트웨이
- **프라이빗 서브넷(앱)**: 애플리케이션 서버
- **프라이빗 서브넷(DB)**: 데이터베이스

AZ마다 하나씩, 두세 벌. 이제는 너무 당연해서 생각도 안 하고 만든다.

그런데 문득 이상했다. **2013년 12월, 처음 AWS를 쓰기 시작했을 때는 이런 걸 본 기억이 없다.** EC2를 띄우고, RDS를 만들고, 그냥 썼다. 서브넷을 나눈다는 개념 자체를 몰랐다. 내가 공부가 부족했던 걸까, 아니면 그때는 서브넷을 나누는 기능이 아예 없었던 걸까. 찾아봤다.

## 결론: 기능은 오래전부터 있었다

내 기억과 달리, 기능이 없었던 게 아니었다.

- **2009년 8월**, VPC가 베타로 나왔다. 이때는 회사 데이터센터와 VPN으로만 연결하는 격리된 네트워크였고, 인터넷으로 나가는 길은 없었다.
- **2011년 3월**, 인터넷 게이트웨이, 라우트 테이블, 네트워크 ACL이 들어왔다. 지금 쓰는 "퍼블릭·프라이빗 서브넷" 구성은 이때부터 가능해졌다. 같은 해 8월 VPC가 정식 출시됐다.
- 그 뒤로 "퍼블릭 서브넷과 프라이빗 서브넷을 둔 VPC"는 AWS 문서와 콘솔 마법사에 나오는 대표 구성이 됐다.

그러니 내가 처음 AWS를 쓸 때도 서브넷은 얼마든지 나눌 수 있었다. 그럼 왜 본 기억이 없을까.

## 못 본 이유: 기본 VPC

답은 **기본 VPC(default VPC)** 였다.

AWS는 2013년 3월부터 기본 VPC를 내놓았고, 2013년 12월 4일 이후에 만든 계정에는 리전마다 기본 VPC가 미리 만들어져 있다. 그 전에는 EC2를 VPC 없이 띄우는 EC2-Classic 방식이 있었는데, 이때부터 새 계정은 VPC만 쓰게 됐고, 대신 아무 설정 없이도 바로 쓸 수 있도록 VPC를 하나 깔아 준 것이다([AWS 문서](https://docs.aws.amazon.com/vpc/latest/userguide/work-with-default-vpc.html)).

기본 VPC는 이렇게 생겼다.

| 항목 | 기본 VPC |
|---|---|
| CIDR | `172.31.0.0/16` |
| 서브넷 | AZ마다 하나씩, 각 `/20` |
| 서브넷 종류 | **전부 퍼블릭** (인터넷 게이트웨이로 가는 라우트가 있음) |
| 퍼블릭 IP | 인스턴스를 띄우면 자동으로 붙음 |

EC2를 만들 때 VPC를 따로 고르지 않으면 이 기본 VPC에 들어간다. RDS도 마찬가지다. 그래서 처음 쓰는 사람은 VPC나 서브넷을 한 번도 만들지 않고도 서버와 DB를 띄울 수 있다. 서브넷은 이미 있었고, 다만 **전부 퍼블릭 하나뿐이라 나눌 일이 없었던 것**이다.

내가 AWS를 처음 쓴 2013년 12월은 마침 새 계정에 기본 VPC가 깔리기 시작한 바로 그 무렵이다. 결국 "기능이 없었다"가 아니라 "기본값이 너무 친절해서 볼 일이 없었다"가 맞다.

## 퍼블릭·프라이빗은 설정 이름이 아니다

찾아보면서 하나 더 알게 된 게 있다. AWS 콘솔에서 서브넷을 만들 때 "퍼블릭" 또는 "프라이빗"을 고르는 칸은 없다. 퍼블릭이냐 프라이빗이냐는 **그 서브넷에 연결된 라우트 테이블**이 정한다.

```text
퍼블릭 서브넷의 라우트 테이블
  10.0.0.0/16  → local
  0.0.0.0/0    → igw-xxxx    ← 인터넷 게이트웨이로 바로 나감

프라이빗 서브넷의 라우트 테이블
  10.0.0.0/16  → local
  0.0.0.0/0    → nat-xxxx    ← NAT 게이트웨이를 거쳐서만 나감 (들어오는 길은 없음)
```

- 기본 경로(`0.0.0.0/0`)가 인터넷 게이트웨이로 가면 퍼블릭 서브넷이다.
- NAT로 가거나 아예 없으면 프라이빗 서브넷이다.

"앱 서브넷", "DB 서브넷"도 마찬가지로 AWS 기능 이름이 아니라 **설계 관례**다. 프라이빗 서브넷을 용도별로 나눠 두고, 보안 그룹과 네트워크 ACL로 "앱 서브넷에서만 DB 포트로 접근" 같은 규칙을 거는 것이다. AWS 쪽에서 이름이 붙은 건 RDS를 어떤 서브넷들에 둘지 정하는 **DB 서브넷 그룹** 정도다.

이름이 붙은 기능이 아니니, 기본 VPC만 쓰던 시절의 나에게는 더더욱 보일 리가 없었다.

## 지금은 처음부터 보인다

지금 VPC 콘솔에서 VPC를 만들면 **"VPC 등"(VPC and more)** 옵션이 있다. AZ 개수, 퍼블릭·프라이빗 서브넷 개수, NAT 게이트웨이, S3 게이트웨이 엔드포인트까지 고르면, 만들어질 서브넷과 라우트 테이블을 그림(리소스 맵)으로 미리 보여 주고 한 번에 만들어 준다([AWS 블로그](https://aws.amazon.com/blogs/aws/new-visualize-your-vpc-resources-from-amazon-vpc-creation-experience)).

요즘 AWS를 시작하는 사람은 VPC를 처음 만드는 순간부터 퍼블릭·프라이빗 서브넷을 보게 된다. 내가 "요즘은 당연하다"고 느낀 데에는 이런 화면의 영향도 있을 것 같다.

## 정리

- 퍼블릭·프라이빗 서브넷 구성은 VPC에 인터넷 게이트웨이가 들어온 2011년부터 있던 기능이다. 처음 AWS를 쓸 때 못 본 건 기능이 없어서가 아니다.
- 2013년 12월 이후 계정에는 리전마다 기본 VPC가 있고, 그 서브넷은 **전부 퍼블릭**이다. EC2와 RDS를 그냥 만들면 여기에 들어가니 서브넷을 나눌 일이 없었다.
- 퍼블릭·프라이빗은 서브넷 설정이 아니라 라우트 테이블이 정한다. 앱·DB 서브넷은 AWS 기능이 아니라 설계 관례다.
- 지금은 콘솔의 "VPC 등" 옵션이 퍼블릭·프라이빗 서브넷 구성을 처음부터 보여 준다.
- 운영 서비스라면 기본 VPC를 그대로 쓰기보다 용도별로 서브넷을 나눈 VPC를 따로 만드는 게 좋다. DB가 인터넷에서 닿는 서브넷에 있을 이유는 없다.
