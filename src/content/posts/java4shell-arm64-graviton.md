11월 중순, 패치 공개 전부터 "JVM에 인증 없이 원격 코드 실행이 가능한 취약점이 있다, 날짜를 정해 패치가 나온다"는 엠바고 공지가 돌았다. 나중에 **CVE-2026-114938**, 흔히 Java4Shell로 불리게 된 취약점이다. Oracle 기록 기준으로 CVSS 3.1 **8.1**(AV:N/AC:H/PR:N), 컴포넌트는 Compiler, 영향 버전은 17.0.21, 21.0.13 등 당시 최신 빌드였다.

운영 중인 Java 서비스가 여럿이라 처음에는 긴장했다. 결론부터 말하면 **우리 서버는 해당이 없었다.** 서버를 새로 만들 때 전부 Graviton(arm64, aarch64)으로 만들어 두었기 때문이다.

## 취약한 코드는 x86-64 전용 경로에 있었다

공식 CVE 기록에는 CPU 아키텍처 이야기가 없다. 하지만 공개 직후 나온 분석들은 원인을 같은 곳으로 짚었다.

- 문제는 JIT 컴파일러가 `java.util.Base64`를 빠르게 하려고 쓰는 **인트린직(intrinsic)**, 그중에서도 **x86-64의 AVX-512 VBMI 명령어로 만든 경로**에 있다.
- 그래서 이 경로를 실제로 쓰는 건 AVX-512 VBMI를 지원하는 x86-64 CPU(Intel Ice Lake 이후, AMD Zen 4 이후 등)에서 도는 JVM뿐이다.
- **arm64 JVM과, AVX-512 VBMI가 없는 x86-64 CPU는 영향이 없다.** ([Sophos 공지](https://www.sophos.com/en-us/security-advisories/sophos-sa-20261118-java4shell), [Tenable FAQ](https://www.tenable.com/blog/java4shell-cve-2026-114938-frequently-asked-questions-about-openjdk-rce-vulnerability))

즉 "Java 버전"만 보면 영향 범위에 들지만, **어느 CPU에서 도는가**까지 보면 빠진다.

## 우리 쪽에서 확인한 것

"Graviton이니까 괜찮겠지"로 끝내지 않고, JVM이 도는 곳의 **버전과 CPU 아키텍처**를 실제로 확인했다. EC2 인스턴스라면 인스턴스 정보에, 컨테이너라면 작업 정의에 아키텍처가 나오고, 인스턴스 안에서는 `java -version`과 `uname -m`으로 바로 볼 수 있다.

```bash
# 인스턴스 아키텍처
aws ec2 describe-instances \
  --query 'Reservations[].Instances[].[InstanceId,Architecture]' --output text

# 인스턴스 안에서 실제 JVM 버전과 CPU
java -version; uname -m
```

결과는 단순했다. JVM은 전부 arm64(aarch64) 위에서 돌고 있었다. 다만 버전만 보면 쓰던 JDK 빌드는 영향 범위에 들어 있었다. 그래서 "버전상 해당, 아키텍처상 비해당"으로 정리하고, 패치는 **급하게 따로 넣지 않고 정식 경로로** 받기로 했다.

## 패치 순서: 급하지 않으니 정식 경로를 기다렸다

수정 빌드는 공개 당일 Corretto 자체 저장소(yum.corretto.aws)에 먼저 올라왔고, 하루쯤 뒤 OS 패키지 저장소에 들어왔다. 관리형 플랫폼 이미지와 공식 컨테이너 이미지는 그보다 늦다.

x86-64에서 AVX-512 VBMI CPU를 쓰는 서버였다면 Corretto 저장소에서 바로 받아 넣거나, 우회 옵션이라도 걸었어야 했을 것이다. 우리는 영향이 없으니 이렇게 정했다.

- Corretto 저장소에서 수동으로 받아 넣지 않는다.
- 플랫폼 이미지와 공식 컨테이너 이미지가 나오면, 외부에 노출된 것부터 차례로 올린다.
- 그 사이 공개 공격 코드가 나오거나 영향 범위가 바뀌면 다시 판단한다.

취약점이 터진 날 할 일이 "밤새 긴급 패치"가 아니라 "영향 없음을 확인하고, 평소 배포 흐름으로 올리기"가 된 셈이다.

## 주의: x86 우회 옵션을 arm64에 그대로 쓰면 JVM이 안 뜬다

공개 직후 우회 방법으로 몇 가지 JVM 옵션이 돌았다.

- `-XX:-UseBASE64Intrinsics`: Base64 인트린직 자체를 끈다.
- `-XX:UseAVX=2`: AVX-512를 쓰지 않게 한다.

이 중 **`-XX:UseAVX=2`는 x86 전용 옵션이라 arm64 JVM에서는 인식하지 못하는 옵션으로 처리되어 JVM이 시작되지 않는다.** "일단 전 서버에 우회 옵션부터 넣자"며 공통 설정에 넣었다면, 영향도 없는 arm64 서버들이 오히려 전부 내려갈 뻔했다. 우회 옵션을 넣을 때도 아키텍처를 먼저 봐야 한다.

## Graviton으로 만든 게 보안 대책은 아니다

이번에는 운이 좋았다고 보는 게 맞다. Graviton을 고른 건 보안 때문이 아니었고, 다음 취약점은 arm64 쪽에만 있을 수도 있다. 다만 이번 일로 남은 교훈은 있다.

- **취약점 공지의 "영향 버전"만 보고 판단하지 않는다.** 실제 취약한 코드 경로가 어떤 CPU, 어떤 옵션에서만 도는지까지 봐야 진짜 영향 범위가 나온다.
- **인벤토리를 바로 뽑을 수 있어야 한다.** 어디서 어떤 JVM이 어떤 아키텍처로 도는지 몇 분 안에 셀 수 있었기 때문에, 공개 당일에 "영향 없음"을 확인하고 정식 패치를 기다리는 결정을 할 수 있었다.
- **아키텍처를 한 가지로 맞춰 두면 판단이 빠르다.** 전부 arm64였기 때문에 "어느 서버가 x86인가"를 하나하나 따질 필요가 없었다.

## 정리

- CVE-2026-114938(Java4Shell)은 JIT의 Base64 인트린직 중 **x86-64 AVX-512 VBMI 경로**에 있는 문제로 분석됐다. arm64(Graviton) JVM은 해당이 없다.
- Java 버전으로는 영향 범위였지만, JVM이 전부 arm64 위에서 돌고 있어 실제 영향은 없었다. 그래서 수동 패치 대신 정식 플랫폼·이미지 업데이트를 기다렸다.
- `-XX:UseAVX=2` 같은 x86 전용 우회 옵션은 arm64에서 JVM을 띄우지 못하게 만든다. 우회 옵션도 아키텍처를 보고 넣는다.
